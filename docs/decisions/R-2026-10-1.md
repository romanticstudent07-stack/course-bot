## Р-2. ДОСТУП УЧАСТНИКА (пункт A2, D-10 «Остаётся») — РЕШЕНО АВТОРОМ 17.10.2026
Суть противоречия: miniapp-security-checklist.md §3 — оплата внутри онбординга
до создания pid; AGENTS.md «Связь с Mini App» (SEAM-1) — участник создаётся при
первом запуске Mini App, оплата была флажком доступа; errata-unified ADD3 — только
возрастной гейт до pid. Решением Р-1 оплата ушла из продукта — шаг «payment» из
порядка онбординга исчез, противоречия по порядку больше нет.
Решение Автора (17.10.2026), схема доступа:
1) оплата — в личной переписке с Автором (вне продукта);
2) Автор шлёт участнику ссылку на бота + персональное кодовое слово (у каждого
   участника своё слово);
3) участник нажимает Start;
4) бот пишет участнику: «введите промокод»;
5) участник пишет слово;
6) бот шлёт в тему Рабочей группы (админ-тема) сообщение «слово + ID» с кнопками
   [Выдать доступ] / [Запретить];
7) после кнопки «Выдать доступ» бот пишет участнику, что можно продолжать;
8) участник проходит онбординг в Mini App: возраст → согласия → участник создан
   (pid). Тот, кому доступ не выдан, видит нейтральный экран «доступ не открыт»
   и участником не становится.
ID участника никто не узнаёт руками: бот получает его сам на Start
(tg_user_registry уже работает — отчёт сервера 17.10).
Механизм для ШТАБа: флажок «доступ выдан» у tg_user_id (префлаг SEAM-1 без оплаты);
команда Панели Автора для выдачи/запрета — новая, в реестре 35 команд её нет
(правки Панели — в DOCS). Имя команды и тексты сообщений — позже, в карточках задач.
Кнопки в админ-теме — как модерационный класс сообщений (канон 7.9); тексты — в карточках.
[поправка ШТАБа 19.10: tg_user_registry хранит уже созданного участника (pid) — флажок «доступ выдан» хранить в НОВОЙ таблице по tg_user_id (миграция, задача Р-2); tg_user_id бот берёт из апдейта Start.

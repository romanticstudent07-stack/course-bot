## Поздняя первая доставка

Не сдвигать дату автоматически. Если операция ещё не применена и исходная дата уже недопустима — показать отказ и запросить новое подтверждение. Если применена — вернуть прежний результат. Не вводить часовой срок намерения.

Канон: Блок 2, П.1, П.3, П.7. Конкретную обработку поздней доставки уточнил Автор: подтверждение на исходную дату не переносится автоматически на другую. И2, `idempotency_keys.ttl_by_kind.default: 1h`, задаёт TTL ключа, а не срок намерения участника.

## Область конфликтного 409

Очистка и аудит безопасности — только при доказанной коллизии op-id. Обычный бизнес-отказ — сообщение и перечитывание состояния, без удаления черновиков.

Канон: `docs/architecture/normative/I2-wave-b.md`, `idempotency_keys.behavior_on_collision`: `conflicting_params: return 409 + log conflict event`. В `docs/architecture/normative/I4-wave-d.md`, `mini_app_client.R339_indexeddb_cache.conflict_ux.on_server_409`, буквальный триггер назван `on_server_409`; для него указаны `action: full IndexedDB wipe on next open` и `log: security_audit event client_op_id_conflict`. Уточнение ограничивает этот триггер доказанной коллизией, а не любым HTTP 409. Это уточнение ещё предстоит отразить в DOCS и синхронизировать по установленному циклу.

## Сохраняемые данные очереди

Разрешены минимальные служебные метаданные операции: вид, неизменные аргументы, op-id, привязка владельца и расписание повторов. Токены, initData, содержимое ответов и снимок участника не сохранять. Метаданные не называть анонимными. Удаление при завершении операции и полную очистку при смене пользователя включить в обязательные проверки.

Канон: `docs/architecture/normative/I4-wave-d.md`, `mini_app_client.R339_indexeddb_cache.write_queue.persistence`: `IndexedDB (survives page reload)`; `mini_app_client.R380_cleanup`: `on_webapp_close: wipe sensitive fields within 24h TTL guarantee`, `on_tg_user_id_change: full wipe immediately`. Автор уточнил состав данных, а не способ исполнения очистки. Это не обещание выполнить код на выключенном устройстве. Очистка при следующем открытии не равна гарантии удаления за 24 часа. Остальные требования R380 не отменены.

## Носитель события client_op_id_conflict (22.11.2026)

Решение Автора 22.11 (К-4 №1, вариант C): событие client_op_id_conflict пишется долговечной записью в новую отдельную таблицу security_events, в отдельной транзакции, чтобы запись не терялась при откате транзакции запроса перед ответом 409. privacy_audit_log (152-ФЗ, доступ к ПДн) для этого не используется; строка серверного лога без записи в БД аудитом не считается.

## Поздняя доставка: форма (22.11.2026)

Решение Автора 22.11 (К-4 №1 окна pause-api-a2, вариант А): клиент присылает в POST /pause/request дату начала паузы start_date (местная дата, YYYY-MM-DD), подтверждённую участником. Операция ещё не применена, а дата уже не совпадает с датой, которую сервер считает началом паузы, — отказ 409 PAUSE_REFUSED (reason start_date_passed) и новое подтверждение; применена — прежний результат. start_date входит в сверку параметров повтора. Имя поля и reason — [ШТАБ-тех], карточка docs/tasks/pause-api-a2.md.

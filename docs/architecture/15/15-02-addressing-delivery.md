# БЛОК 15 · ШАГ 2 — АДРЕСАЦИЯ И ДОСТАВКА КОНТЕНТА

Шаг проектирует путь контента от конфига до ленты так, чтобы доставка была надёжной при сбоях, устойчивой к повторам и злоупотреблениям, а каждое сообщение имело точный адрес в реестре. Разбит на четыре развилки, вместе образующие единый механизм.

## Развилка 1. Протокол доставки

Протокол доставки — трёхфазный, устраняющий проблему двойной записи (бизнес-состояние в нашей БД и факт отправки в Telegram нельзя записать одной транзакцией). Фаза намерения: атомарно, в одной PG-транзакции с бизнес-решением «выдать день N», в реестр пишутся строки-намерения (pending) без message_id. Фаза отправки: сообщения физически уходят в Telegram. Фаза подтверждения: по факту успеха строка получает реальный message_id и статус active. Оборванные pending-строки подхватывает фоновый досыльщик. Это каноничный транзакционный outbox с polling-досыльщиком — та самая реализация «фонового сверщика confirmed-но-не-delivered» из Блока 16. Паттерн честно даёт «хотя бы один раз», а не «ровно один раз», поэтому идемпотентность на нашей стороне обязательна.

## Развилка 2. Единица доставки и классификатор сообщений

Единица доставки — день как несколько сообщений (модель B): пять блоков заданий, каждый — отдельное сообщение со своими кнопками, у пятого блока дополнительно кнопка «Отправить отчёт». Причина: Telegram не привязывает кнопки к середине сообщения — «под каждым блоком свои кнопки» возможно только если каждый блок отдельное сообщение; плюс обход лимита длины и гранулярность удаления. Каждый блок нумеруется: номер служит и содержательным адресом (бот проверяет отчёт по конкретным блокам), и инженерным (логический адрес для идемпотентности и частичной досылки). Полный адрес сообщения — participant_id + module + day + block_number.

Классификатор сообщений — три класса, которые нельзя смешивать, реализуются одним полем type. Контент курса (блоки заданий, ссылки внутри, приглашение к рефлексии от бота, ответы и реакции Автора) — удаляется при рефанде. Служебные (напоминания, уведомления об очереди, мотивационные) — не удаляются никогда. Транзакционные/юридически значимые (подтверждения оплаты, факты возвратов, согласия) — хранятся неизменяемо. Граница удаления при рефанде та же, что в Шаге 1.

## Развилка 3. Идемпотентность и лимит

Идемпотентность и лимит — два независимых слоя, работающих строго последовательно: сначала идемпотентность («это то же действие или новое?»), потом лимит («новому действию разрешено сейчас?»). Технический повтор никогда не расходует лимит; только по-настоящему новый запрос доходит до атомарной проверки-и-списания лимита. Защита от дублей — три уровня: клиентский (мгновенная деактивация кнопки + обязательный answerCallbackQuery, чтобы UI не завис), серверный (ключ идемпотентности participant_id+day+purpose в быстром хранилище с коротким TTL ≈ секунды; повтор → пустой ack, без выдачи и списания), концептуальная граница (дубль против нового определяется фактом списания лимита). Это закрывает окно дедупликации из случая 7.7 Блока 13.

Лимит — три полноценные выдачи задания дня за скользящие 24 часа (по часовому поясу участника). Одна выдача — заход в «Пройденное», выбор дня, получение полного текста без кнопок для ознакомления. Считаются выдачи, а не уникальные дни. Скользящее окно, а не календарные сутки — чтобы закрыть эксплойт границы полуночи; для честного участника разница незаметна. Технически лимит — не счётчик, а COUNT записей с временными метками за интервал now−24h..now: переживает перезапуск, не требует ночного обнулятора. Проверка-и-списание атомарны (блокировка строки участника). Записи о выдачах содержат поля для будущей детекции — участник, день, метка времени, признак «засчитано в лимит» — чтобы лимит и детекция питались из одного источника.

## Развилка 4. Частичный сбой доставки

Частичный сбой доставки — досылаем, не откатываем. Досыльщик видит по реестру, какие блоки active, какие pending, и досылает недостающие в порядке возрастания номера, не трогая доставленные и отметки участника. Намерение на весь день фиксируется атомарно, поэтому досыльщик всегда знает идеальный состав дня. Кнопка «Отправить отчёт» появляется только с доставкой пятого блока — отправить неполный день технически невозможно. Флуд-контроль Telegram (ошибка «слишком много запросов» с retry_after; жёсткий известный предел ≈1 сообщение/сек в один чат): досыльщик читает время ожидания, ждёт ровно столько, повторяет тот же блок; это не считается провалом и не увеличивает счётчик неудач. Выборка pending с блокировкой и пропуском заблокированных (SELECT … FOR UPDATE SKIP LOCKED) не даёт двум экземплярам взять одну строку. Настоящие ошибки увеличивают счётчик; при пороге блок помечается проваленным с алертом. Здоровье доставки отслеживается по возрасту старейшей необработанной строки. Сознательно отвергнуты CDC/Debezium (polling-задержка некритична) и брокеры Kafka (потребитель — сам Bot API, а не микросервисы).

Разграничение: логика активности кнопки «Отправить отчёт» (активна только когда всё отмечено) принадлежит Блоку 3; Блок 15 физически довозит пятый блок с кнопкой. Открытых вопросов нет.

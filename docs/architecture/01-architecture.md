# БЛОК 1. ОБЩАЯ АРХИТЕКТУРА

> **Переопределено ERRATA-UNIFIED и SEAM-PATCH-1.** Входящий долг из Б14 (реестр `tg_user_id ↔ pid`) читается через ERRATA `X-DEBT-14` и SEAM-1: точка создания участника — first-launch Mini App, автосоздание через Mini App разрешено. Роли `finance`, `moderator`, `helper` дополнены патчами И1/Б17. Флаги фич (`feature_flags_miniapp`) вводятся И1. См. [normative/I1-wave-a.md](normative/I1-wave-a.md), [normative/errata-unified.md](normative/errata-unified.md), [normative/seam-patch-1-onboarding.md](normative/seam-patch-1-onboarding.md).

## 1.1. Двухуровневая архитектура (принцип)

Система разделена на два уровня. Логика — в коде (правила прохождения, механика жизней, гейтинг, таймеры). Контент и структура — в конфигурации (YAML/БД): количество модулей, дней, тексты заданий, ссылки на материалы, параметры дней. Это позволяет Автору добавлять новые модули/этапы и менять контент без изменения кода — просто дописывая конфигурацию.

## 1.2. Количество этапов/модулей

Бот не хранит число модулей в коде. Он читает структуру из конфигурации. При добавлении модуля 5, 6, 7… Бот сразу «видит» его. Курс расширяем бесконечно — концепция «изменение себя — пожизненная история», финиша нет.

## 1.3. Новые модули видят ВСЕ участники

При добавлении нового модуля он становится доступен всем участникам (в т.ч. завершившим прошлый «конец»). Уведомление о доступности нового модуля предусмотрено (детали в Блоке 14).

## 1.4. Технологический стек (рекомендация)

PostgreSQL — основное хранилище (не SQLite). Redis — вспомогательный буфер/кэш (только для некритичных данных, см. 1.6). Celery / APScheduler — отложенные задачи (дедлайны, паузы, сводки, напоминания, эффект очереди). Linux / Docker — среда исполнения. Сервер на старте: Intel Pentium N3700, 8 ГБ RAM, 1 ТБ HDD; архитектура заложена под миграцию на VPS.

## 1.5. Отложенные задачи (принцип планирования)

Бот не опрашивает всех участников постоянно. На каждое событие с дедлайном создаётся одна отложенная задача (Celery eta / APScheduler), которая срабатывает в нужный момент по ТЗ Участника. При выполнении условия раньше срока задача отменяется. Масштабируется до тысяч участников на текущем железе.

## 1.6. Принцип сохранности данных (основа-основ)

Все данные, касающиеся прогресса, жизней, замеров, оплаты и рефлексий, критичны. Пишутся надёжно и синхронно в PostgreSQL, НЕ через быстрый буфер. Redis-буфер допустим только для некритичного (аналитика, служебные метки). Детальная архитектура durability (WAL, бэкапы 3-2-1, point-in-time recovery, персистентность) ресёрчится и проектируется в Блоке 14.

## 1.7. Принцип «журнал событий вместо перезаписи»

Всё важное хранится как журнал событий с датами, а не как перезаписываемое текущее значение. Это касается: замеров, списаний/возвратов жизней, платежей, пауз, откатов. Это снимает большинство вопросов «что обнуляется» и защищает историю.

## 1.8. Персистентность состояния

FSM-состояние Участника хранится в БД, не в оперативной памяти. При перезапуске/падении Бота состояние не теряется.

## 1.9. Веб-админка (задел на будущее)

На старте управление — через Рабочую группу (см. Блок 17). Веб-панель (FastAPI) закладывается архитектурно на будущее для масштабирования на сотрудников.

## 🛡 Блок 1 — Fail-safe

Инвариант сквозной нумерации модулей валидируется на уровне конфигурации (см. Патч-1, П1). FSM-состояние персистентно (1.8). Критичные данные пишутся синхронно в PostgreSQL, Redis только для аналитики (1.6). Журнал событий вместо перезаписи защищает историю (1.7).

Входящий долг из Блока 14

Блок 14 передал в Блок 1 три сущности, которых в теле v3 нет. Первая — реестр соответствия `tg_user_id ↔ pid`, который Б14 только читает и на котором стоит авторизация Mini App. По ERRATA (`X-DEBT-14`, отклонение прежней формулировки) и SEAM-PATCH-1 (`autocreate_source: mini_app_only`) точкой создания участника является **first-launch Mini App** — не бот-диалог. При отсутствии `tg_user_id` в реестре Mini App запускает штатный конвейер онбординга (возрастной гейт → правовое → оплата → анкета → Чек-Ап), а не отдаёт 403; регистрационный тупик при недоступности Mini App канонизирован как проектное решение (SEAM-PATCH-1). См. [normative/errata-unified.md](normative/errata-unified.md) и [normative/seam-patch-1-onboarding.md](normative/seam-patch-1-onboarding.md).

## YAML — базовая структура (Блок 1)

```yaml
# ============================================================
# БЛОК 1 — Общая архитектура
# Версия: consolidated v3
# ============================================================
modules:
  - id: 1
    days: 14
  - id: 2
    days: 14
  # добавление нового модуля = добавление блока сюда;
  # бот сразу "видит" его, курс расширяем бесконечно

architecture:
  layers:
    logic: code            # правила, гейтинг, жизни, таймеры
    content: yaml_db       # модули, дни, тексты, ссылки, параметры
  storage:
    primary: postgresql    # всё критичное — синхронно
    cache: redis           # ТОЛЬКО некритичное (аналитика, метки)
  scheduler: celery_or_apscheduler   # 1 отложенная задача на событие с дедлайном
  runtime: [linux, docker]
  fsm_state: persisted_in_db          # переживает перезапуск (1.8)

data_integrity:
  event_journal_not_overwrite: true   # замеры, жизни, платежи, паузы, откаты (1.7)
  critical_writes: synchronous_postgres
  durability_detail: block_14         # WAL, бэкапы 3-2-1, PITR

new_modules:
  visible_to: all_participants        # включая завершивших
  notify: block_14

web_admin:
  mvp_control: working_group          # Блок 17
  future: fastapi_panel               # задел на масштабирование
```

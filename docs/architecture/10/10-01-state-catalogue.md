> **Примечание к нарезке (не текст оригинала).** Шаг 1 пересматривает модель, объявленную в Шаге 0: вместо двух равноправных осий — одна эксклюзивная ось `lifecycle_phase` плюс STATUS-множество, а пара `phase × effective_modifier` понижена до производной проекции для UI. Действующая редакция модели — Шаг 1. См. [10-00-contract.md](10-00-contract.md), раздел «Модель состояния — двухосевая».

## Часть 1 — Выжимка (детальный текст логики, без ролей, без мета)

### 1.1. Базовая модель состояния

Состояние участника Блока 10 описывается одной эксклюзивной осью-STATE и набором STATUS-флагов, а не плоским перечислением (enum) и не «двумя равноправными осями».

Единственная истинно эксклюзивная ось — это `lifecycle_phase` (фаза жизненного цикла): участник в каждый момент находится ровно в одной фазе, и фаза определяет, какие переходы вообще возможны.

Всё остальное, что раньше называлось «второй осью модификаторов» и «третьей осью видимости», по своей природе является STATUS — набором наблюдательных признаков, которые могут сосуществовать одновременно и служат для управления доступом, отрисовки экранов, подсчётов и логов. Такое разделение соответствует паттерну «State vs Status»: состояние (state) отвечает на вопрос «где участник в жизненном цикле», статус (status) — «что именно с ним сейчас происходит».

Карточный `status` из Блока 6 остаётся проекцией (производным отображением), а не источником истины.

### 1.2. Ось фаз (lifecycle_phase) — эксклюзивная

Фазы — это стабильные, значимые узлы жизненного пути, между которыми переходы редки и осмысленны:

**`pre_road`** — техническая нулевая фаза. Запись участника уже существует, но места на «дороге курса» ещё нет. Дорога курса начинается только с первой подтверждённой оплаты. До неё участник несёт признак неоплаты первого этапа и находится вне активного контура. Это начальный узел матрицы переходов Шага 2.

**`active`** — участник на дороге курса, оплатил текущий этап, идёт по дням/модулям.

**`pending_erasure`** — предтерминальная «замороженная» фаза. Вход — запрос на удаление данных (по инициативе участника или по требованию закона). Внутри — окно исполнения удаления (по нормам GDPR — обычно до 30 дней, в сложных случаях до 90). В этой фазе все входящие бизнес-события (оплата и прочее) отбиваются, чтобы не возникало гонок во время удаления. Единственный выход — в `erased`.

**`erased`** — терминальная точка. Идентифицирующие данные удалены, остальное обезличено; финансово- и юридически-обязательные записи сохранены по закону. Участника как личности в системе больше нет. Это легитимный конец жизненного цикла, а не «тупик-ловушка».

Важно: оплата и архив НЕ являются отдельными фазами. Оплаченность/неоплаченность и «спящий/архив» выражаются через STATUS-флаги (см. ниже), потому что участник в любом из этих режимов остаётся в одной и той же фазе жизненного цикла (`active` либо `pre_road`), меняется лишь контекст.

### 1.3. Модификаторы — как STATUS-множество + resolver

Модификаторы — это набор одновременно активных флагов (status-множество), а не один эксклюзивный слот. В реальности признаки сосуществуют: участник объективно может быть одновременно и не оплатившим (`freeze_unpaid`), и забаненным (`ban_mod`). Поэтому все активные модификаторы хранятся параллельно, со своими атрибутами и историей.

Каталог модификаторов (6):

- **`normal`** — полноправное значение (не null), «ничего не наложено».
- **`pause_user`** — пользовательская пауза (сущность и правила — Блок 2). Накладывается только в момент старта паузы; стадии заявки (запрошена/одобрена/отложена/перенос) живут в Блоке 2, а не на оси Блока 10.
- **`pause_shadow`** — «тайная» системная пауза-страховка (правила — Блок 7.7). Невидима участнику (маскирующий экран), лимит паузы участника не тратит, с неоплатой не конфликтует. Вход — только автоматически по фазе C механизма 7.7; выход — вердикт. Также применяется в кейсе «догнал контент внутри оплаченного этапа».
- **`block_lives`** — блок по исчерпанию жизней (сущность — Блок 2). Детали перехода «потеряна 3-я жизнь → `block_lives`» — в Шаге 2.
- **`ban_mod`** — модераторский/авторский бан. Один тип, снимает только Автор, авто-снятия нет. Атрибуты: `reason` (обязателен), `appeal: none | pending | resolved`. Апелляция доступ не возвращает, только запускает пересмотр. Правила «за что банят» — Блок 7; Блок 10 владеет только реакцией жизненного цикла на факт бана.
- **`freeze_unpaid`** — заморозка по неоплате (стык Блок 16). Атрибут `scope`: `pre_first_stage` (доступа почти нет — только бот/поддержка) либо `pre_next_stage` (плюс доступ к успешно завершённым заданиям предыдущих этапов, стык Блок 13).

Эффективный модификатор — это не хранимое значение, а результат чистой детерминированной функции-resolver над набором активных флагов, по лестнице приоритета. Resolver выдаёт ровно одно решение для гейтинга доступа и для отрисовки экрана.

Черновая лестница приоритета (сильнее → слабее): `ban_mod` > `block_lives` > `freeze_unpaid` > `pause_shadow` > `pause_user` > `normal`. Финальный порядок фиксируется в Шаге 2, где будут известны все переходы.

Двухосевая проекция `phase × effective_modifier` сохраняется как производная для UI и матрицы переходов, но источник истины — набор флагов, а не проекция.

### 1.4. Видимость (visibility) — STATUS

Видимость в активном контуре — это status-флаг с двумя значениями: `in_scope` (участник считается в списках, графиках и сводках) и `out_of_scope` (исключён из них). Гашение и включение происходит единым флагом сразу для всех трёх поверхностей (списки, график, сводки одновременно) — чтобы не возникало рассогласованных отчётов (в списке нет, а в графике есть).

Применение:

- «Спящий» = `freeze_unpaid` + `in_scope` (окно 4–10 дней неоплаты: заморожен, но ещё считается).
- «Архив» = `freeze_unpaid` + `out_of_scope` (10+ дней: убран из контура, прогресс сохранён/заморожен).
- Неоплата первого этапа (`pre_first_stage`) — всегда `out_of_scope` сразу (считать нечего, рефлексий ещё нет); деление спящий/архив к ней не применяется.
- Снятие `out_of_scope` → `in_scope` происходит только по событию подтверждённой оплаты, никогда по таймеру (вход по времени, выход по событию — асимметрия намеренная).

### 1.5. «Жизни», «догнал», «выпускник» — это STATUS, не состояния

Счётчик потерянных жизней (1/2/3) — status-счётчик, не отдельное состояние (само блокирующее событие — это модификатор `block_lives`, а счётчик — контекст).

`content_frontier_reached` («догнал весь доступный контент») — status-флаг. Поскольку биллинг поэтапный: если участник догнал внутри оплаченного этапа и нового контента ещё нет — система автоматически применяет `pause_shadow` (без траты лимита), снимаемый при выкладке; если участник прошёл весь этап целиком — активируется статус «Выпускник этапа» с предложением купить следующий этап (Шаг 7). Задолжать «за воздух» при поэтапной оплате невозможно.

«Выпускник» (B16) — status-флаг на фазе `active`, не отдельная фаза. «Вечный выпускник» (прошёл весь существующий курс) — тот же флаг, но resolver видит, что следующего этапа не существует, и показывает режим удержания «жди нового контента» вместо апселла. Это гарантирует отсутствие тупика: выход из «вечного выпускника» — появление нового этапа.

### 1.6. Инварианты и жёсткие требования Шага 1

Переходы абсолютны (SET…WHERE, идемпотентны) и журналируемы с триггером-владельцем (append-only). Событие подтверждённой оплаты — атомарное, меняющее сразу и модификатор (`freeze_unpaid` → `normal`), и видимость (out → in), и позицию фазы, чтобы исключить гонку (стык durability — Блок 15). Нет пустых экранов ни в одном состоянии. Все callback-и привязаны к `participant_id`. Деньги идемпотентны. Ручной и провайдерский пути оплаты не дублируются.

Требования, вынесенные на проверку в следующие шаги: у каждого состояния есть выход (нет trap-state) — Шаг 2; нет недостижимых состояний — Шаг 2; защита от устаревших/повторных/переупорядоченных событий (at-least-once) — Шаг 8; resolver обязан иметь полный набор unit-тестов на все комбинации флагов, включая невозможные пары (невозможная пара → явная ошибка, не тихий выбор) — Шаг 8.

block_10_step1_catalogue:
  version: "1.0-final"
  model:
    principle: "State vs Status (S3-паттерн)"
    exclusive_state_axes:
      - lifecycle_phase        # единственная истинно эксклюзивная ось
    status_dimensions:         # сосуществуют, для доступа/UX/подсчётов/логов
      - modifiers_set          # набор флагов + resolver
      - visibility
      - lives_counter
      - content_frontier_reached
      - graduate_flag
    source_of_truth: "phase + набор status-флагов"
    ui_projection: "phase × effective_modifier (ПРОИЗВОДНАЯ, не истина)"
    card_status_block6: "проекция, не источник истины"

  lifecycle_phase:
    type: exclusive_enum
    values:
      pre_road:
        desc: "запись есть, места на дороге нет; до первой оплаты"
        carries: { modifier: freeze_unpaid(scope=pre_first_stage), visibility: out_of_scope }
        is_initial_node: true
      active:
        desc: "на дороге курса, текущий этап оплачен"
      pending_erasure:
        desc: "предтерминал; окно исполнения удаления (GDPR ~30, до 90 дн)"
        frozen: true
        incoming_business_events: rejected   # антигонка
        exits_to: [erased]
      erased:
        desc: "терминал; идентиф. данные удалены, обязательное сохранено"
        terminal: true
        trap_state: false

  modifiers:
    representation: status_set          # НЕ один слот; флаги сосуществуют
    stored: "все активные флаги + атрибуты + история"
    effective_modifier:
      type: derived
      via: pure_resolver_function
      priority_draft: [ban_mod, block_lives, freeze_unpaid, pause_shadow, pause_user, normal]
      priority_final: "Шаг 2"
    catalogue:
      normal:        { owner: B10, note: "полноправное значение, не null" }
      pause_user:    { owner: B2,  applied_at: "старт паузы", substates_live_in: B2 }
      pause_shadow:  { owner: B7.7, visible_to_user: false, uses_user_pause_limit: false,
                       enter: "auto фаза C 7.7", exit: "вердикт",
                       also_used_for: "догнал внутри оплаченного этапа" }
      block_lives:   { owner: B2,  transition_detail: "Шаг 2 (3-я жизнь)" }
      ban_mod:       { owner_rules: B7, owner_lifecycle_reaction: B10,
                       single_type: true, auto_lift: false, lifted_by: author_only,
                       attrs: { reason: required, appeal: [none, pending, resolved] },
                       appeal_restores_access: false }
      freeze_unpaid: { owner: B16,
                       attrs: { scope: [pre_first_stage, pre_next_stage] } }

  visibility:
    type: status_flag
    values: [in_scope, out_of_scope]
    single_flag_covers: [lists, graph, summaries]   # гасит все три РАЗОМ
    mapping:
      sleeping: "freeze_unpaid + in_scope (неоплата 4-10 дн)"
      archive:  "freeze_unpaid + out_of_scope (неоплата 10+ дн)"
      pre_first_stage: "out_of_scope сразу; деление спящий/архив не применяется"
    enter_out_of_scope: "по таймеру (10+ дн)"
    return_in_scope: "ТОЛЬКО по событию confirmed-оплаты, никогда по таймеру"

  status_flags:
    lives_counter: { type: counter, values: "0..3", not_a_state: true }
    content_frontier_reached:
      type: bool
      caught_up_inside_paid_stage: "→ auto pause_shadow, снятие при выкладке контента"
      whole_stage_done: "→ graduate_flag + апселл след. этапа (Шаг 7)"
    graduate_flag:
      type: bool
      on_phase: active
      eternal_graduate: "resolver: нет след. этапа → режим 'жди контента', НЕ trap-state"

  invariants:
    - transitions_absolute_idempotent: "SET...WHERE"
    - append_only_journal_with_trigger_owner: true
    - payment_confirmed_atomic: "modifier+visibility+phase одним событием (стык B15)"
    - no_empty_screens: true
    - callbacks_bound_to_participant_id: true
    - money_idempotent: true
    - manual_and_provider_payment_paths_not_duplicated: true

  hard_requirements:
    T1: { desc: "каждое состояние имеет выход (нет trap-state)", verify_at: "Шаг 2" }
    T2: { desc: "нет недостижимых состояний", verify_at: "Шаг 2" }
    T3: { desc: "защита от устаревших/повторных/reordered событий (at-least-once)", verify_at: "Шаг 8" }
    T4: { desc: "resolver — чистая функция + полные unit-тесты на ВСЕ комбинации флагов; невозможная пара → явная ошибка, не тихий выбор", verify_at: "Шаг 8" }

  contract_requests:

  deferred:

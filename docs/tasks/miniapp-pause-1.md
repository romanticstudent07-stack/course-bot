## 2. Цель
Новый /paused: бюджет, запрос паузы на 1–7 дней с завтра, состояние заявки, отмена, досрочное продолжение.
Активная пауза не должна открывать экран дня. Ошибка проверки паузы также не открывает день; «Помощь» доступна.
Существующие фазы входа, 18+, согласий, номера и незавершённого онбординга не менять.

## 7. Контракт API (T3 §4; сверен с routers/pause.py@b92698a)
Общий префикс /miniapp/v1. apiRequest сохраняет текущие базовый URL, initData-заголовок и credentials.
GET /pause → 200:
    {budget_days_left:number, budget_days_total:number, cycle_ends_at:string|null,
     pause:null|{id:number,status:string,start_at:string,planned_end_at:string}, can_request:boolean, refusal:string|null}
GET возвращает только открытую user-паузу requested/approved/active, иначе pause=null; завершённой истории нет.
Открытая пауза → refusal="already_open", can_request=false; это не запрет cancel/resume.
Без открытой паузы can_request вычислен для days=1: не гарантирует разрешения выбранных N дней.
POST /pause/request: тело {days:целое 1..7}, X-Client-Op-Id UUID4 → 201 {pause:объект как в GET}.
Старт/конец вычисляет сервер: завтра 00:00 по поясу участника и местная дата старта + N, 00:00.
Повтор того же op-id возвращает ту же заявку, тело повтора сервер не сравнивает.
POST /pause/cancel: без тела и X-Client-Op-Id → 202 {status:"accepted"}; для requested/approved.
POST /pause/resume: без тела и X-Client-Op-Id → 202 {status:"accepted"}; для active.
Ошибки {code,message,details?}: общие 401, 404 PARTICIPANT_NOT_FOUND, 422 VALIDATION_ERROR, 429 RATE_LIMITED, 503 SERVICE_UNAVAILABLE.
Специальные 409: PAUSE_ALREADY_OPEN; PAUSE_REFUSED с details.reason; PAUSE_NOT_CANCELLABLE; PAUSE_NOT_ACTIVE.
Причины правил: not_approved, block_lives, state, gap_24h, stage_taken, no_budget; already_open — только GET.
not_approved совместим со старым контрактом, но не основание обещать сгорание заявки; неизвестная причина → нейтральная заглушка.
Сохранить details как unknown с безопасным чтением reason; не показывать произвольные message/details сервера.
202 означает принятие события, не новый статус: после POST перечитать GET. Повтор cancel/resume после применения может дать 409 — это норма.
## 8. Поведение экрана и навигации
- /paused доступен только внутри фазы app; вход из готовой /me. Прямой hash не обходит вход/онбординг.
- Перед монтированием /day, включая корень и неизвестный маршрут через fallback, выполнить GET /pause.
- Пока GET не завершён — день не монтировать; active → /paused с replace; requested/approved/null → обычный день.
- Ошибка или неизвестный status паузы → нейтральная заглушка и «Повторить», без дня; существующая «Помощь» остаётся доступной.
- /help и /me не запирать этой проверкой; возвращение из них к /day снова проходит GET. Не создавать цикл редиректов.
- На /paused показать бюджет left/total, конец цикла при наличии, статус и границы текущей паузы; null не называть отклонением.
- pause=null: запрос доступен только при can_request; целые 1–7, не больше budget_days_left; причины — местные заглушки.
- requested/approved: отдельные подписи и «Отменить»; active: канонический экран паузы, три полосы, ETA по planned_end_at и «Продолжить».
- ETA — оставшееся время, не локальный час телефона; истечение таймера вызывает GET, но само статус не меняет и день не открывает.
- Для requested/approved запланировать GET на start_at, затем до 5 повторов через 2 с при прежнем статусе; далее ручное «Обновить».
- После cancel/resume: заблокировать повтор действия, GET сразу и до 5 повторов через 2 с до смены/исчезновения той же паузы; затем ручное «Обновить».
- Не считать 202 завершением. После исчезновения паузы предложить переход к дню через защитную проверку; немедленных заданий не обещать.
- 409 → заглушка по коду и перечитывание GET; 401/404/422/429/503/сеть → безопасная заглушка, без автоповтора POST.
- При 429 сохранить Retry-After; до его истечения не делать фоновые повторы GET и отключить повтор запроса; затем ручное действие.
- На попытку request сохранить в памяти пару {days,op-id}; неопределённый сетевой/503 результат повторять с той же парой.
- Пока исход request неопределён, days не менять; успешный GET с открытой паузой снимает необходимость повторять request.
- При отправке исключить двойное нажатие; после 201 перейти к чтению состояния, а не считать паузу уже активной.
- Устаревшие ответы после нового запроса/ухода игнорировать; таймеры очищать. Данные/попытки только в памяти, не в URL, логах или хранилищах.

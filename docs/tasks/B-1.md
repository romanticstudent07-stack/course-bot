## 7. Контракт
- Фиксированное окно 1 минута: ключ `rl:miniapp:{tg_user_id}:{unix_minute}`, INCR; если результат 1 — EXPIRE 120.
  Результат > rate_limit_per_minute → 429.
- 429: тело Error {code: "RATE_LIMITED", message: «Слишком много запросов. Подождите минуту.»},
  заголовок Retry-After = секунд до конца минуты (1..60).
- Порядок: require_init_data → rate_limit. Без initData → 401, счётчик не трогается. rate_limit получает контекст
  через Depends(require_init_data) — FastAPI кэширует его в запросе, повторной проверки HMAC нет.
- /healthz и /security/csp-report не лимитируются (они вне miniapp_v1).
- fail-open: пустой REDIS_URL или ошибка Redis → запрос проходит, WARNING
  «rate-limit: redis unavailable (<ИмяИсключения>), fail-open». Текста исключения, initData, URL в логе нет.
- Клиент: redis.Redis.from_url(settings.redis_url, socket_timeout=…, socket_connect_timeout=…), кэш на процесс.
  Счётчик за интерфейсом (зависимость get_counter), тесты подставляют фейк.
- config: rate_limit_per_minute: int = Field(60, ge=1); rate_limit_redis_timeout_seconds: float = 0.2.
- Самопроверка: `python -m app.rate_limit selftest` — INCR/EXPIRE ключа `rl:selftest` в настоящем Redis,
  печать «rate-limit selftest: OK» или «FAIL <ИмяИсключения>», exit 0/1.

## 9. Тесты (без БД и без настоящего Redis — фейковый счётчик с подставным временем)
60 запросов → 200, 61-й → 429 + Retry-After в 1..60; разные tg_user_id считаются отдельно; новая минута
сбрасывает счёт; ошибка счётчика → запрос проходит + WARNING в caplog без tg_user_id и initData;
без initData → 401 и счётчик не вызван; /healthz не лимитируется; limit=2 из настроек → третий 429.
Цель check.sh: api. CI: те же тесты (Redis в CI не нужен).

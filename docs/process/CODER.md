## Бюджет: максимум 3 запроса Автора
- Запрос — только сообщение Автора с новым содержанием (лог, ошибка, ответ, вопрос).
  «Далее» и «Повтори часть k» в бюджет 3 запросов НЕ считаются (правила выдачи — «Формат пакета»).
- З1: план пакета + части 1–2. План задачи не пересказывай — карточка уже утверждена.
- «Далее» → следующие части (не больше 2 за ответ), пока пакет не кончится.
- «Повтори часть k» → часть k ЦЕЛИКОМ заново под тем же номером.
- З2: исправление по логу.
- З3: исправление по логу (последняя попытка по одной и той же ошибке).
- CI зелёный → в том же ответе, где был последний фикс, или отдельным коротким ответом —
  блок «ИТОГ ДЛЯ ШТАБА». Закрытие задачи (проверка PR, комментарий, мерж, задание серверу)
  делает ШТАБ, не КОДЕР.
- Не уложились → блок ПЕРЕДАЧА, Автор открывает новое окно КОДЕР.

## Формат пакета
- Каждая часть — ОДИН блок кода с языком text. Внутри — только блоки:
      ===== FILE: путь/от/корня/репо =====
      полный текст файла
      ===== END =====
      ===== DELETE: путь/от/корня/репо =====
- Файл — ЦЕЛИКОМ. Запрещены «...», «остальное без изменений» и т.п. — tools/unpack.py отклонит.
- ПАМЯТКА UNPACK (урок 29.10, бережём 5-часовой лимит Автора): tools/unpack.py отклоняет пакет
  из-за строк-заглушек и фраз-заглушек в ЛЮБОМ файле, и в .md тоже (в комментариях тестов, notes,
  описаниях). Точный список — PLACEHOLDER_LINES и PLACEHOLDER_PHRASES в tools/unpack.py; ШТАБ
  вставляет его в каждый старт, З2 и З3. Под каждой частью — строка «Самопроверка unpack: ✅».
  Отказ только из-за фразы в словах (не строка-заглушка в коде) и Автор сказал ШТАБу «п.2 — да» →
  Автор правит сам: code .tmp/bundle.txt → Ctrl+G номер строки → фразу заменить на «как есть» →
  Ctrl+S → unpack заново.
- ПАМЯТКА РАЗМЕР (урок 30.10): у файлов с лимитом размера (docs/STATE.md ≤ 20 480 Б,
  docs/DEFECTS-FOUND.md < 25 000 Б, docs/decisions/DECISIONS.md ≤ 8 192 Б, другие — по карточке
  или старту) байты оценить ДО выдачи (кириллица 2 Б), цель ≤ 85 % лимита (15 360 → ≤ 13 000).
  Не влезает — резать ДО выдачи. Под частью — «Самопроверка размера: ≈N Б из L ✅»
  (файлов с лимитом нет — «Самопроверка размера: лимитов нет ✅»). Автор после unpack проверяет wc -c.
- Исключение (ШТАБ, 02.10): правила в docs/process/*.md цитируют запрещённые фразы. Если unpack
  отклонил пакет ТОЛЬКО из-за такой цитаты в docs/process/*.md — раскладывать с
  python3 tools/unpack.py --allow-placeholder .tmp/bundle.txt и написать это в ИТОГЕ.
  Для любых других файлов флаг запрещён: ошибка unpack → назад КОДЕРУ.
- В .md-файлах внутри пакета не используй строки из трёх обратных кавычек (ломают блок):
  примеры кода — отступом 4 пробела.
- Правила выдачи пакета (решение Автора, 02.10, процесс v3.5):
  1. В начале З1 — план: «Пакет: N частей. Часть 1: <файлы>; часть 2: <файлы>; …».
     Номера и состав частей потом НЕ меняются.
  2. В одном ответе — не больше 2 частей. Файл никогда не делится между частями.
  3. Каждая часть заканчивается строкой «КОНЕЦ ЧАСТИ k из N: файлов M» (последняя строка
     внутри блока части; unpack.py её пропускает). Нет строки — часть оборвалась.
  4. После 2 частей — стоп и строка «Части 1–2 из N готовы. Напишите: Далее»
     (дальше так же: «Части 3–4 из N готовы. Напишите: Далее»).
  5. «Повтори часть k» → часть k ЦЕЛИКОМ заново под тем же номером. Никаких «частей N+1»
     как исправлений и пояснений вместо файлов.
  6. «Далее» и «Повтори часть k» в бюджет 3 запросов НЕ считаются. Запрос — только сообщение
     с новым содержанием.
- Пакет исправления (З2, З3) выдаётся по тем же правилам 1–5, со своим планом частей.
- Часть — примерно до 350 строк. После последней части строка: «КОНЕЦ ПАКЕТА: частей N, файлов M».
- Первый файл пакета З1 — docs/STATE.md с внесёнными строками от ШТАБа.
  Строк нет — STATE.md не трогай.
- Разрешённые пути — как в tools/unpack.py. Нельзя: docs/architecture/**, .github/**, .githooks/**, .env.
  Нужна правка .github/** → отдельный блок «ДЛЯ РУЧНОЙ ПРАВКИ» с полным текстом файла
  и списком отличий от main (Автор вносит сам через сайт). Имена job в ci.yml не менять:
  это имена обязательных проверок (ruleset main-ci-lock).
- Миграция добавляет или удаляет таблицы → в пакет apps/api/tests/expected_tables.txt
  целиком, с полным новым списком. ci.yml не трогаем.
- Новый файл *.sh → в Блоке 2 команд после unpack строка: chmod +x <файл> (check.sh проверит).
- Тексты курса (дни, задания, сообщения бота) — только заглушки: репо публичный.
- Новые зависимости — только если есть в карточке.

## Под пакетом З1 — команды для Codespaces (ЕДИНЫЙ ВИД, решение Автора 30.10)
Одинаково у ВСЕХ окон: КОДЕР, ПРОЕКТИРОВЩИК, ИССЛЕДОВАНИЕ, З1/З2/З3. Меняется только вид команд
терминала; пакет, части, «Далее», шаги, PR, ИТОГ, ПЕРЕДАЧА — как в остальных разделах.
Ровно 3 код-блока. В блоках только команды, без комментариев (исключение из SHTAB.md 1-А.4);
пояснения — текстом над блоком и под ним. gh не использовать (в Codespaces его нет).
Подставь ветку, цели и текст коммита из карточки.
Блок 1 — после него Автор вставляет ВСЕ части пакета подряд в .tmp/bundle.txt → Ctrl+S:
    cd /workspaces/course-bot
    git checkout main && git pull
    git checkout -b <ветка из карточки>
    mkdir -p .tmp && code .tmp/bundle.txt
Блок 2 — проверка:
    python3 tools/unpack.py .tmp/bundle.txt
    wc -c <файлы с лимитом размера>
    chmod +x <новый файл *.sh>
    bash tools/check.sh <цели из карточки>
    git add -A && git status
  Строка wc -c — только если в пакете есть файл с лимитом размера; chmod +x — только если есть
  новый *.sh; иначе этих строк в блоке нет. Пакет только из docs — bash tools/check.sh без целей.
  check.sh сам проверяет eol и exec.
Блок 3 — только после успешной проверки (unpack «ГОТОВО», check зелёный, в git status — ожидаемые файлы):
    git commit -m "<текст коммита>"
    git push -u origin <ветка>
Терминал покажет ссылку на создание PR → PR на сайте GitHub. Заголовок PR и описание PR
(по AGENT-BRIEF.md, раздел 10) — отдельными код-блоками.
Репо DOCS-course-bot — те же 3 блока, но cd /workspaces/DOCS-course-bot и bash tools/checks.sh
без целей (DESIGNER.md, «DOCS-репо»).
Образец Автора (30.10, ИССЛЕДОВАНИЕ iter3) — так должно выглядеть всегда:
    cd /workspaces/course-bot
    git checkout main && git pull
    git checkout -b docs/research-iter3
    mkdir -p .tmp && code .tmp/bundle.txt
  (Автор вставляет файлы)
    python3 tools/unpack.py .tmp/bundle.txt
    wc -c docs/research/iter3.md
    bash tools/check.sh
    git add -A && git status
  (после успешной проверки)
    git commit -m "docs(research): iter3 — исследование Итерации 3 «Чек-Ап и Карточка»"
    git push -u origin docs/research-iter3

## Общение с Автором (он новичок)
- Формат: «Шаг N. Ты, где: что». Перед каждым блоком — что это, куда, что увидишь, если не так.
- Термины — одной фразой. Не выдумывай: нет данных — спроси.
- Файл — одним блоком целиком, никогда не кусками.
- Терминал: Автор не вставляет в терминал больше ~10 строк за раз и не использует heredoc
  (cat <<EOF …) — это запрещено. Файлы — через редактор (code <файл>) или пакет + tools/unpack.py;
  в терминал — только короткие команды, один блок команд — до ~10 строк.

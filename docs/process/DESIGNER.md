## Бюджет окна (CB-process-1, решение Автора 09.10)
Урок 08.10: в З1 прочитано ≈ 50 файлов вместо ≈ 25 из списка; ответ шёл так долго, что окно
казалось зависшим, история чуть не сжалась. Принцип как у КОДЕРА (SHTAB.md, 3-Б): чтение не
урезаем — делим задачу и окна. ПРОЕКТИРОВЩИКУ можно читать больше, чем КОДЕРУ (у КОДЕРА ≈ 130–140 КБ).
1. Список и лимит считает ШТАБ до старта: «обязательно» (размер каждого файла, итог в КБ) и
   «по необходимости». В итог входит база: этот файл, docs/process/PACK.md, docs/STATE.md,
   AGENT-BRIEF.md (итог базы ШТАБ пишет в старте). docs/process/README.md в базу не входит
   (решение Автора 12.11). Лимит «обязательно»: окно ПОЛНОЕ или КАРТОЧКИ — до 170 КБ,
   окно ИССЛЕДОВАНИЕ — до 200 КБ (его вывод короткий).
2. Окно = 1–3 карточки одной области (как у КОДЕРА в 3-Б). Больше — ШТАБ делит заранее.
3. Тип окна выбирает ШТАБ:
   - ПОЛНОЕ — всё влезает в 170 КБ: З1 исследование и вопросы → З2 карточки → З3 правки.
   - Больше 170 КБ — два окна. ИССЛЕДОВАНИЕ: З1 — чтение, файл docs/research/<пачка>.md целиком
     одним блоком и вопросы Автору; З2 — ответы Автора и замечания ШТАБа → исправленный файл
     целиком; З3 — запас. КАРТОЧКИ: пишет карточки по файлу исследования, а не по исходникам;
     читает базу, файл исследования и только файлы, из которых нужны выдержки в карточки.
4. Сверх списков — до 3 файлов, каждый в «Прочитано» с отметкой «сверх списка» и причиной.
   Нужно больше — не читай: в ответе список «надо дочитать» с причинами, решает ШТАБ.
5. Вывод З2 — только карточки: не больше 3, каждая до 150 строк. docs/STATE.md и другие большие
   файлы не переписывай: нужные строки дай списком «Для ШТАБА» — ШТАБ передаст их Автору
   правкой на сайте.
6. Время: в старте ШТАБ пишет ожидаемое время З1 (обычно до 10 минут, ИССЛЕДОВАНИЕ — до 15).
   Пока ответ идёт, Автор ничего не отправляет. Прошло вдвое больше и текст не меняется →
   Автор идёт в ШТАБ.

## Окно = 3 запроса (урок И1, 30.09)
После 3 запросов история окна сжимается и теряется. Поэтому окно рассчитано ровно на 3 запроса.
- З1 — ГЛУБОКИЙ. Читай список из старта (раздел «Бюджет окна»). Ответ: задачи по 2–3 строки,
  порядок и почему, вопросы Автору — с номерами, кратко и просто (варианты, плюсы/минусы, мнение).
  В конце З1, под строкой «ПЕРЕДАЧА: …» (PACK.md, раздел 6), обязательно список «Прочитано:» —
  пути, КБ и 1 строка главного факта (сверх списка — с отметкой).
- З2 — ПАКЕТ. Автор приносит одним сообщением ответы Автора и замечания ШТАБа.
  Заново не читай то, что есть в «Прочитано»; дочитывай только новое, что понадобилось из-за ответов.
  Выдай карточки (не больше 3) пакетом + шаги Codespaces (ветка docs/tasks-<пачка>, PR без мержа)
  + ИТОГ ДЛЯ ШТАБА (PACK.md, раздел 6) с полем «Для ШТАБА: <строки STATE или „нет“>».
- З3 — ПРАВКИ. Замечания ШТАБа одним сообщением. Читай только файлы, которых касается правка.
  Выдай ТОЛЬКО изменённые файлы целиком (формат пакета) — Автор кладёт их поверх в ту же ветку.
- Не успел за 3 запроса → последний ответ заканчивается ИТОГОМ с полем «ДОДЕЛАТЬ»: что готово,
  что осталось (по пунктам), какие файлы нужно прочитать. Дальше — новое окно (старт ниже).
- Четвёртый запрос в том же окне — нельзя. «Далее» и «Повтори часть k» — не запросы:
  запрос — только сообщение с новым содержанием.

## Карточка docs/tasks/<id>.md — обязательные разделы
1. id, заголовок PR, ветка, режим (Р0+ / Р1-П / Р1), зависит от (id задач).
2. Цель (2–4 строки).
3. Решения Автора, которые касаются задачи (дословно).
4. Выдержки архитектуры — цитаты с путём файла и номером раздела. КОДЕР архитектуру не читает.
5. ЧТО ПРОЧИТАТЬ: точный список файлов кода для правки.
6. Файлы: создать / изменить / удалить (полные пути).
7. Контракт: эндпоинты, поля, типы, коды ответов и ошибок.
8. БД: миграция (имя, revision и down_revision, таблицы, поля, индексы, ограничения, downgrade).
   Добавляет или удаляет таблицы → в разделе 6 файл apps/api/tests/expected_tables.txt
   с полным новым списком таблиц (по нему CI сверяет БД; ci.yml не трогаем).
9. Тесты: список (что проверяет каждый); цели tools/check.sh; что проверит только CI.
10. Живые проверки на сервере после мержа (команды, ожидаемый результат, бэкап до миграции).
11. Запреты (из AGENT-BRIEF.md, раздел 3, плюс специфичные для задачи).
12. Критерии готовности. 13. Оценка: часы Автора, кредиты (0 для Р0+).
14. РЕВЬЮЕР: да / нет. «Да» — если задача трогает initData, 18+, согласия (B-2),
    rate-limit (B-1), роли/GRANT БД (B-3) или оплату.

## Размеры
- Задача: до 12 файлов и примерно до 600 строк кода. Больше — разрежь.
- Бюджет чтения КОДЕРА (SHTAB.md, 3-Б): одна карточка = одна область (Mini App ИЛИ API ИЛИ docs);
  без исследований — их делаешь ты, в карточку кладёшь вывод; файлы, которые не читаются
  за раз целиком, КОДЕРУ не давать. В разделе 5 — размер каждого файла (КБ) и итог «Чтение КОДЕРА ≈ N КБ».
- Задачи с миграциями БД не объединять и не вести параллельно. down_revision новой
  миграции = revision последней миграции в main или в предыдущей карточке цепочки;
  в карточке напиши «начинать после мержа задачи X».
- Мелочи из docs/STATE.md («Мелочи») подкладывай в подходящие задачи без БД.
- Карточка — до 150 строк. В .md не используй строки из трёх обратных кавычек.

## DOCS-репо (DOCS-course-bot) — правки канона (настроено 25.10)

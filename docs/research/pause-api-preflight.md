## Владелец операции

По main.py/pause.py доверенный вход — ctx.tg_user_id из require_init_data.
active_pid_locked находит активный pid, берёт participant:pid и повторно
проверяет tombstone. Это не привязка сохранённой операции к прежнему pid.
Протокол остальных писателей tombstone не прочитан; полная гонка не закрыта.

По participants.py новый INSERT использует uuid.uuid4(); после tombstone
возможна новая регистрация прежнего Telegram ID с другим pid.
InitData подтверждает Telegram ID, но не поколение локальной попытки.

| Сценарий | Риск |
|---|---|
| Попытка A отправлена с initData аккаунта B | request может впервые примениться к B. |
| Старый pid tombstone, нового нет | Активного участника нет; писать нельзя. |
| Тот же Telegram ID, новый pid | Старый op не найден в новой области; возможно первое применение. |
| cancel/resume после смены паузы | finish может выбрать другую текущую строку. |

[канон I4 §R380/AD-02; I2 §stable_key_recipes]
Нужны изоляция владельца и область pid. Telegram ID, op-id и локальный
замок не различают поколения участника.

Предложение ШТАБу: минимальная серверная предпосылка —
поколение владельца сохранённой попытки совпадает с действующим pid,
независимо полученным из проверенной initData под замком.
Для cancel/resume неизменная цель дополнительно принадлежит этому pid.

Возможный механизм — выданная сервером непривилегированная привязка
поколения, однозначно связанная с pid. Конкретное поле не утверждено.
Client-supplied pid/owner_ref не является авторизацией: нельзя получать
по нему действующего участника или выдавать результат другого pid.
Новый marker нельзя автоматически подставлять в старую попытку.
Отсутствующая предпосылка не означает согласие действующего владельца.
Гейт защищает неизменную сохранённую попытку от нового контекста,
но не удостоверяет историю произвольно переписанных клиентом метаданных.

Рекомендуемый порядок:
замок → проверка владельца → доказанный повтор/сверка аргументов →
бизнес-условия → атомарная запись результата и доменного события.
Получение действующего pid остаётся только через проверенную initData.
Несовпадение владельца само по себе не доказывает коллизию op-id;
код отказа здесь не назначен.

## Влияние на API

[канон I2 §behavior_on_collision; Автор, канон проверен R]
Готовы требования, не форма API:
- UUID операции для трёх POST; неизменные аргументы и предпосылка владельца.
- Для cancel/resume — неизменная цель, не новая текущая пауза.
Ключ действия по pause_id и квитанция попытки имеют разное назначение.
- Request: доказанный повтор до бизнес-проверок. Первая поздняя доставка
не переносит дату: отказ и новое подтверждение; применённой — прежний результат.
- Доказанная коллизия отличима от бизнес-409; только она включает аудит/wipe.
- Результат/квитанция и новая доменная запись/событие атомарны, где применимо;
повтор не создаёт второго события. Аудит отказа требует отдельной фиксации.

По pause.py _pause_out читает текущие status/даты, не неизменный первый ответ.
По 0007 params_hash nullable; наличие колонки не даёт отпечатков старых
операций. Без исходных параметров нельзя доказать совпадение или коллизию.

[канон I2 §ttl_by_kind/gc] default 1h — TTL ключа, не намерения.
Канон задаёт почасовое удаление истёкших ключей; реализация GC не проверена.
Исчезнувшая квитанция не разрешает повторное применение.
Нужны доказательства результата/аргументов на весь срок восстановления.
Выводить исходные days из изменяемых дат без проверки нельзя.

[Автор, канон проверен R §Границы подтверждения]
owner_ref, expected_start_at, server_now, valid_until не утверждены;
часовой срок намерения не вводится. До очереди определить совместимость:
старый небезопасный POST не может быть fallback. B/C не проектируются.

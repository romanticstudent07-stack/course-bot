## Расхождения и границы

К-2/К-4. Запрет карточки уступает R339: исключение и отсрочка отвергнуты. Текущий API расходится с И2: «тело повтора не сравнивается» (§7), тогда как И2 требует `conflicting_params: return 409 + log conflict event`. Отдельный API-контракт обязателен: клиент не может устранить это расхождение, закрыть гонку GET→POST или гарантировать прежнюю дату, которую сервер сейчас вычисляет заново.

У R339 заголовок `conflict_ux`, но буквальный триггер `on_server_409:`. На API `PAUSE_ALREADY_OPEN`, `PAUSE_REFUSED`, `PAUSE_NOT_CANCELLABLE`, `PAUSE_NOT_ACTIVE` означают бизнес-отказ, не коллизию параметров. И2 привязывает 409 и аудит именно к `conflicting_params`. Для карточки ШТАБу подтвердить трактовку по К-4: проект ниже использует wipe только по доказанной коллизии; буквальная широкая формулировка R339 не объявлена исправленной. Если нужна правка формулировки — в DOCS с синхронизацией, не в зеркале. В OVERRIDES нет замен четырёх узлов; E1 относится к проекции.

R380 не даёт механизма физического удаления на закрытом устройстве: close/pagehide лишь best effort, таймер и service worker не гарантия. Поэтому в паузе не сохранять поля, требующие гарантированной фоновой очистки. Минимальные ссылки на владельца и паузу — всё равно связанные с участником метаданные, не «анонимные». До карточки ШТАБу подтвердить классификацию этих полей и охват wipe. Если требуется физическое удаление самих метаданных на закрытом клиенте, данный браузерный дизайн этого не обеспечивает; TTL при следующем открытии не выдавать за гарантию. Никакого молчаливого ослабления R380.

## Минимальный API (предложение К-5, отдельная карточка)

- GET /pause остаётся источником статуса. Добавить `owner_ref` — стабильную непривилегированную ссылку на текущий pid, например SHA-256 от доменного префикса и UUID pid; `request_start_at` — серверное «завтра», и `server_now`. Ссылку не считать токеном доступа. Контекст получения GET должен принадлежать тому же Telegram-пользователю; после смены аккаунта получить новый. Не включать новую очередь до наличия нового контракта, не откатываться на старые POST при его отсутствии.
- Три POST требуют UUID4 `X-Client-Op-Id`, `owner_ref` и `valid_until`; request дополнительно `days, expected_start_at`; cancel/resume — `pause_id`. Эти поля неизменны. Сервер под `active_pid_locked` сверяет `owner_ref` с pid из проверенной initData. Для cancel/resume ищет только `(pid, pause_id)`, никогда «текущую подходящую»; сохраняет проверки статуса и ключей часов. Для первого request серверное «завтра» обязано совпасть с `expected_start_at`, иначе отказ без переноса даты. `valid_until` при создании не более часа от наблюдённого `server_now`; сервер не применяет впервые после срока и отклоняет срок более часа вперёд. Это ограничение намерения, не TTL снимка.
- Для трёх POST использовать пространство `user_pause:{pid}:{client_op_id}`; hash канонических полей, включая вид операции, дату/цель, срок, версию формата. Сначала проверить владельца и найти квитанцию, затем сравнить hash, затем — только для новой записи — проверять срок, дату и бизнес-условия. Запись результата (`result_ref` = id паузы), INSERT заявки или события и соответствующий ключ действия фиксируются атомарно. Повтор request → 201 с той же строкой, включая закрытую; cancel/resume → 202 для того же результата, даже если исходная пауза закрыта. Прежние ключи действий по pause_id остаются вторым барьером, в том числе от другого op-id. TTL новых квитанций — 1 ч [И2 default]; у прежних cancel/resume — 3650 дней, это не TTL клиентской операции.
- Сейчас request ищет `(pid, client_op_id)` в participant_pauses вне TTL. Сохранить эту защиту от повторного INSERT. Если квитанции уже нет, но строка request найдена, не применять запись повторно и не утверждать, что параметры совпали: отдельный ответ «результат есть, параметры не сверяемы». То же для старых заявок без hash. Новый UUID не генерировать автоматически. Клиент не шлёт POST после своего срока; сервер до любых новых эффектов проверяет срок даже после GC. Старый контракт §7 и тест, принимающий изменённые days, не переносить в новый режим; совместимость и порядок выката явно описать в карточке.
- Предлагаемые коды 409: `CLIENT_OP_ID_CONFLICT` только при несовпадающем hash; отдельные неколлизионные коды для смены владельца, устаревшего намерения и несверяемого повтора. При настоящем конфликте сервер пишет структурированный `security_audit` / `client_op_id_conflict` без initData, ключей и тел; бизнес-409 туда не попадают. 0007 уже даёт `params_hash`, `result_ref` и SELECT/INSERT; таблицы `security_audit` нет в expected_tables.txt. Подтвердить канал/сбор аудита до карточки; не подменять `privacy_audit_log` и не считать обычный INFO аудитом. При необходимости изменения GRANT — отдельная миграция и ревью, не скрытая часть Mini App.

## Клиентская очередь (предложение К-5)

Один незакрытый слот на владельца, не FIFO всех экранов. Поля: `v` для строгого декодера/миграции; `kind` для разрешённого транспорта; `opId` для повторов и дедупликации; `args` — ровно параметры контракта; `ownerRef` — серверная принадлежность; локальная метка Telegram-владельца — для обнаружения смены ещё до запроса; `createdAt/validUntil` — срок намерения; `retryCount/nextAt` — backoff после перезапуска; `phase` — различить ещё не отправленное, неопределённое и остановленное. Сохранять только allowlist. Не сохранять PID в открытом виде, имя, тексты сервера, снимок, initData/hash/auth_date или авторизационные секреты. Локальная метка: хеш с префиксом приложения от канонического id, не доказательство личности; не логировать.

1. На старте авторизованной фазы и перед каждым отправлением: прочитать актуальную raw initData тем же SDK, `tgUserIdFromInitData` — только для локального сравнения; проверить также mismatch `Telegram.WebApp.initDataUnsafe.user.id` на load по R380. Пропуск/расхождение источников → не отправлять; подтверждённая смена → остановить старый worker, увеличить поколение, очистить таймеры, отменить локальный fetch где возможно, не принимать поздние ответы, сообщить другим вкладкам; очистить все IndexedDB приложения до запуска новой очереди. Транзакцию на сервере отменённый fetch не откатывает; серверная проверка owner_ref остаётся обязательной. После очистки сверить владельца снова. Конфликт сохраняет отдельный флаг wipe до следующего открытия; сбрасывать флаг только после успешной полной очистки. Если другая вкладка блокирует закрытие DB, держать отправку закрытой, а не считать wipe выполненным.
2. Клик → в общей блокировке прочитать слот и валидировать контекст → `queued` → дождаться `transaction.oncomplete` → перед fetch записать `uncertain`. Ошибка/abort IDB до commit: POST = 0, видимая ошибка, без memory fallback. `uncertain` перед fetch означает «могло уйти» даже после падения до вызова fetch. Один worker на origin под Web Locks, с повторным чтением слота под lock; удерживать до завершения fetch и фиксации исхода. Без поддержки безопасной межвкладочной блокировки — не отправлять. После падения lock освобождается; серверный замок и квитанция защищают от ещё выполняющегося старого POST.
3. Повтор с неизменным телом и op-id: 2 с × 2^n, потолок 60 с; сохранить `nextAt` и счётчик. 429: `nextAt = max(backoff, now + Retry-After, прежний срок)`; без корректного заголовка использовать backoff. 429 после неопределённой попытки не очищает её. Нет сети: не крутить таймеры/POST, перепроверить срок на online/возврате; сеть, 5xx, timeout или неполный успех → `uncertain`. Не рассчитывать на выполнение в фоне после закрытия. Ошибка фиксации после POST → остановить worker, не считать исход подтверждённым; восстановление только через последнюю подтверждённую запись и тот же op-id. Соблюдать записанный срок во всех вкладках.
4. 401/403 → пауза отправки до новой действительной авторизации того же владельца; не цикл POST. 404/422 → остановить автоотправку; после прежней неопределённости не выдавать отказ текущего вызова за доказательство, что первый не прошёл. Бизнес-409 → перечитать состояние; окончательный отказ по этой операции закрывает её, но не запускает другую. Неизвестный 409 → остановка/перечитывание без wipe; настоящий конфликт → блокировка всех пауз, сообщение R339 и wipe на следующем открытии. Не удалять неизвестный формат как «успех» и не отправлять его.
5. Валидный 201/202 → закрыть слот транзакционно и перечитать GET; 202 означает «принято», не «применено». GET с открытой паузой сам по себе не доказывает авторство request: подавить новый клик, не очищать по чужому id. Если исходная пауза закрылась и GET=null, прежний request до срока повторяется с тем же UUID: сервер проверяет квитанцию/старую строку, а не создаёт второй request. Для cancel/resume исчезновение цели — не доказательство, кто её закрыл. Через срок: `expired`, никакого POST/нового UUID; свежий GET и сообщение «исход не подтверждён», затем можно убрать локальную попытку. Новое действие — только отдельное явное подтверждение по свежему состоянию. Никакого сохранения чувствительных полей «до таймера»; закрытие отключает работника и очищает оперативные данные, вход проверяет срок/владельца до чтения очереди в UI.

## Четыре блокера и проверки

1. pause.ts: неопределённая запись → 429 → истечение Retry-After → повтор с теми же days/UUID; проверить отдельно после пересоздания worker и до/после срока операции.
2. start_at ≤ now: один немедленный старт серии для валидной даты; ключ серии `(pause.id, start_at)`, исчерпание запоминается, apply не запускает её снова. Начало в прошлом/ровно now, задержанная смена, максимум 1+5 GET через 2 с, следующий id — новая серия. Таймер не открывает день.

У завершения/отмены одной серии очищаются её busy/polling и таймеры; устаревший ответ не завершает новую. Тесты с отложенными ответами resume/ETA и cancel/start_at в обоих порядках, уход и отсутствие залипания. GET-серии и POST-backoff независимы.

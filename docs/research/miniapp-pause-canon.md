## К-4: вопросы до карточек

**Q1. Поздняя первая доставка.** Канон: проверено И2 `idempotency_keys`/`pause_semantics.user_pause`, И4 R339 и Р-6а/Р-20 — молчат, сколько живёт намерение и можно ли сдвинуть первоначальное «завтра» (§7 карточки, `_bounds` в коде). Если сохранённый request впервые дошёл после смены серверной даты, отклонять его с новым явным подтверждением (рекомендация) или разрешать новую дату по прежнему клику? Уже применённая операция в обоих случаях — восстановление результата. Часовой дедлайн не предлагается как норма.

**Q2. Какой 409 стирает данные?** Канон: проверено И2 `idempotency_keys.behavior_on_collision`: `conflicting_params: return 409 + log conflict event`; И4 `R339_indexeddb_cache.conflict_ux`:

    on_server_409:
      show_error: "локальные данные повреждены; переоткройте Mini App"
      action: full IndexedDB wipe on next open
      log: security_audit event client_op_id_conflict

В коде `PAUSE_ALREADY_OPEN`, `PAUSE_REFUSED`, `PAUSE_NOT_CANCELLABLE`, `PAUSE_NOT_ACTIVE` — бизнес-отказы; статус сам по себе не доказывает коллизию. Уточнить: wipe относится только к подтверждённому несовпадению параметров одного op-id (предложение) или буквально ко всем 409? Узкое чтение не утверждено. Если нужно уточнение: ШТАБ фиксирует ответ, правит путь `mini_app_client.R339_indexeddb_cache.conflict_ux.on_server_409` в DOCS по DESIGNER, синхронизирует до карточки. Зеркало здесь не править.

**Q3. Что считать чувствительным и какой гарантии требует R380?** Канон: проверено И4 R339 `persistence: IndexedDB (survives page reload)` и R380 `on_webapp_close: wipe sensitive fields within 24h TTL guarantee`, `on_tg_user_id_change: full wipe immediately` — классы полей ниже не указаны. Какие из полей подпадают под 24-часовую гарантию и требуется ли для них физическое удаление при закрытом устройстве? Браузер не гарантирует выполнение JS после закрытия: таймер, close/pagehide и service worker не дают такой гарантии. Очистка на следующем открытии — не замена. Если обязательные аргументы чувствительны и требуется физическая гарантия, нужен иной способ хранения до реализации, не исключение из R339/R380.

## Запись и восстановление — проект К-5

Один незавершённый слот на владельца. В таблице «слот» означает до подтверждения/окончательного отказа или согласованной остановки; календарный срок не утверждён. Строки слота удалять транзакционно; каждый такой атрибут также удаляется при полной очистке. Ни одно поле не объявлено нечувствительным.

Не хранить снимок паузы (`snapshot_ttl: 24h` к очереди не относится), PID в открытом виде, initData, hash подписи, токены, тексты и детали ответа. Поля без функции не добавлять; `server_now` не сохранять.

1. На входе и перед POST сверить тег по актуальной raw initData через `tgUserIdFromInitData` только для локального владения; R380 также указывает mismatch `Telegram.WebApp.initDataUnsafe.user.id` на загрузке. Нет ID или источники расходятся — не отправлять. Сервер доверяет лишь проверенной initData. При смене сразу остановить старый worker, очистить таймеры, отменить локальный fetch где возможно, игнорировать поздние ответы, остановить другие вкладки. Полная очистка всех IDB приложения перед запуском нового владельца; при блокировке удаления отправка закрыта. Отмена fetch не откатывает сервер. Охват и механика wipe требуют инвентаризации.
2. Под общим межвкладочным lock: прочитать слот → `queued` → дождаться commit → зафиксировать `uncertain` перед fetch. Ошибка IDB до commit — ноль POST, видимая ошибка, без memory fallback. Кандидат — Web Locks от чтения до фиксации ответа; без безопасного lock не отправлять. После падения вкладки ещё может работать старый серверный вызов: его защищает серверная идемпотентность, не lock браузера.
3. Сеть/таймаут/5xx или неполный успех → прежний `uncertain`; offline — ждать online/возврата. Backoff на op-id, ориентир 2 с × 2^n, потолок 60 с; сохранить расписание, брать максимум с Retry-After и имеющимся сроком ожидания. 429 не стирает прежнюю неопределённость. Ошибка записи после POST → остановка, при восстановлении только прежняя записанная попытка. 401/403 — ждать действительной авторизации того же владельца; 404/422 — остановка без автоцикла, не доказательство исхода первого вызова.
4. 201/202 → закрыть запись после надёжной фиксации, перечитать GET; 202 не означает применения. Открытый GET не доказывает принадлежность попытке, GET=null не доказывает, что её не было. Повторить тот же op-id, только если контракт позволяет безопасно получить результат или применить исходную операцию. При доказанном бизнес-отказе закрыть и перечитать; при неизвестном исходе остановить и сообщить, новый UUID — только после отдельного явного действия. Вариант для настоящей коллизии по Q2: блокировать отправку, зафиксировать флаг, показать текст R339, выполнить wipe на следующем открытии. Бизнес-409 и неизвестный 409 не записывать как доказанную коллизию.
5. Закрытие останавливает worker и очищает RAM насколько позволяет среда. При входе сначала владелец/флаг/проверка актуальности, затем восстановление. Если срок будет принят: после него не инициировать новый эффект; проверить состояние и явно показать неподтверждённый исход. Не обещать физическую очистку на закрытом устройстве.
